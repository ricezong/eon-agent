# Eon Agent 后续升级计划

当前版本为 MVP，仅支持单次命令行对话。以下按优先级分阶段规划后续升级方向。

---

## Phase 1：API 服务化

**目标**：将 Agent 从命令行工具升级为 HTTP 服务，支持多用户并发访问。

- 提供 REST API 接口，接收用户输入，返回 Agent 执行结果
- 支持同步和流式两种响应模式：同步等待完整结果返回，流式实时推送中间过程（思考摘要、工具调用进度、最终输出）
- 会话管理：每个对话分配唯一 sessionId，通过 API 创建、查询、关闭会话
- 多会话并发：不同会话之间状态隔离，互不干扰
- API 认证：简单的 Token 或 API Key 校验，防止未授权访问

---

## Phase 2：多轮对话与会话持久化

**目标**：支持同一会话内的多轮连续对话，用户可以追问、补充信息、调整任务方向。

- 会话恢复：用户可以基于已有 sessionId 继续对话，Agent 自动加载历史上下文
- 上下文衔接：新输入与之前的对话历史自然衔接，不丢失之前的关键信息和任务进度
- 会话超时与回收：长时间不活跃的会话自动归档，释放内存资源
- 会话列表查询：用户可以查看自己的历史会话列表和摘要
- 基于 Checkpoint 的崩溃恢复：服务异常重启后，进行中的会话可从最近一次 Checkpoint 恢复

---

## Phase 3：多模型适配与动态切换

**目标**：支持接入多种 LLM（DeepSeek、通义千问、GPT、Claude 等），根据任务特点动态选择。

- 多模型配置：在 `agent.yaml` 中配置多个 LLM 提供商，各自独立的 base_url / api_key / model_name
- 模型路由策略：简单问答用轻量模型，复杂工具任务用强推理模型，按任务复杂度自动选择
- 运行时切换：用户可以通过参数指定使用哪个模型，或在会话中途切换
- 模型健康检查：定期探测各模型可用性，自动降级到备用模型
- 统一的 Token 统计：不同模型的 Token 计费差异统一折算

---

## Phase 4：工具能力扩展

**目标**：丰富工具生态，覆盖更多实际任务场景。

- **代码执行工具**：安全的沙箱环境执行 Python / JavaScript 代码片段，支持数据处理、格式转换、简单计算
- **数据库查询工具**：连接外部数据库（MySQL / PostgreSQL），支持自然语言转 SQL 查询
- **邮件 / 消息推送工具**：任务完成后通过邮件或即时消息通知用户
- **图片生成工具**：接入文生图模型，根据文本描述生成图片
- **文件格式转换工具**：PDF / Word / Excel / Markdown 互转
- **第三方 API 适配器**：天气、股票、地图等常用第三方 API 的封装工具
- **动态工具加载**：支持运行时通过配置文件或 API 注册新工具，无需重启服务

---

## Phase 5：任务编排与异步执行

**目标**：支持长耗时任务的异步执行和复杂任务编排。

- 异步任务提交：用户提交任务后立即返回 taskId，后台执行，不阻塞 HTTP 连接
- 任务状态查询：通过 taskId 查询任务进度（当前 Turn、已完成步骤、Token 消耗）
- 任务取消：用户可以主动取消正在执行的任务
- 定时任务：支持 cron 表达式定时触发 Agent 执行（如每天早上发送新闻摘要）
- 子任务编排：复杂任务拆分为多个子任务，支持串行 / 并行 / 条件分支编排
- 任务结果通知：任务完成后通过 webhook 或消息推送通知用户

---

## Phase 6：权限控制与安全加固

**目标**：生产级安全能力，支持多用户、多角色、细粒度权限。

- 用户体系：用户注册、登录、会话归属
- 工具权限分级：不同角色用户可使用的工具集不同（如普通用户不能使用 `download` 和 `file_io`）
- 敏感参数脱敏：工具执行日志和返回结果中的 API Key、密码等敏感信息自动脱敏
- 操作审计：记录所有工具调用的操作日志，支持事后审计
- 速率限制：单用户 / 单 IP 的请求频率和 Token 消耗限制
- 沙箱隔离：`file_io` 和 `download` 的文件操作范围按用户隔离，防止越权访问

---

## Phase 7：可观测性与运维

**目标**：完善的监控、告警和运维能力。

- 指标采集：Turn 数、Token 消耗、工具调用成功率、LLM 响应延迟、上下文压缩触发频率等
- 可视化面板：会话列表、任务进度、Token 消耗趋势、工具调用热力图
- 告警规则：LLM 连续失败、Token 预算接近上限、熔断触发等异常自动告警
- 分布式追踪：每个请求的全链路追踪（API → Agent → Hook → LLM → Tool），快速定位性能瓶颈
- 日志聚合：结构化日志输出，支持接入 ELK / Loki 等日志平台

---

## Phase 8：智能增强

**目标**：通过更智能的机制提升 Agent 的任务完成质量和效率。

- **工具选择优化**：根据任务类型和上下文自动推荐最合适的工具，减少 LLM 的工具选择错误
- **动态上下文窗口**：根据任务复杂度动态调整上下文窗口大小，简单任务用小窗口省 Token，复杂任务用大窗口保完整
- **多 Agent 协作**：多个 Agent 分工协作，如一个负责搜索、一个负责分析、一个负责写作，由编排 Agent 统一调度
- **反思与自我纠错**：任务完成后自动回顾执行过程，总结经验教训写入长期记忆，下次类似任务自动复用
- **用户偏好学习**：记录用户的交互习惯和偏好（如喜欢简洁回复、偏好某种工具），逐步个性化
- **Prompt 动态优化**：根据 LLM 的实际表现自动调整系统提示词，如发现 LLM 经常忘记调用 `finish`，在 prompt 中加强引导

---

## 优先级排序

| 阶段 | 优先级 | 理由 |
|------|--------|------|
| Phase 1：API 服务化 | P0 | 从 CLI 到 API 是最基础的能力升级，是后续所有功能的前提 |
| Phase 2：多轮对话 | P0 | 没有多轮对话能力的 Agent 无法用于实际场景 |
| Phase 5：任务编排与异步 | P1 | 长耗时任务必须异步化，否则 HTTP 超时是硬伤 |
| Phase 3：多模型适配 | P1 | 单一模型存在可用性和成本风险 |
| Phase 6：权限与安全 | P1 | 生产部署必须解决安全问题 |
| Phase 7：可观测性 | P2 | 运维必备，但可在功能稳定后补充 |
| Phase 4：工具扩展 | P2 | 工具可以按需逐步添加，不阻塞核心能力 |
| Phase 8：智能增强 | P3 | 锦上添花，在基础能力稳定后再做深度优化 |
